**S2c-2 gate-fix round (this session): three contaminating bugs found and fixed, grazing-angle Path-A verdict still pending a clean look.** Timo's first pass: bump itself worked (on/off clearly visible, relief visible) but three problems blocked judging the real question. **(1) Blinking/near-black patches, moving dark blobs — a real bug, not derivative-bump behaviour, confirmed root cause.** Code inspection confirmed the shadow-path suspicion was NOT it: `StationShadowTerm`/`StationShadowSetup` in both `PS_DynamicLit*` functions always receive the unperturbed `input.StationNorm`, never the bump-perturbed normal — unchanged from the original S2c-2 implementation. The actual bug: `input.RenderPos` is world metres × `Camera3D.RenderScale` (1e-9, `Camera3D.cs`), so `ddx`/`ddy` of it are ~1e-9x smaller than a metre-scale derivative. `PerturbNormalFromHeight`'s `det` (built from two factors carrying that tiny scale) collapsed to ~1e-18 — utterly negligible next to `bumpStrength*surfGrad` (only one power of the tiny scale) for any usable `bumpStrength`. The perturbed normal was really just `normalize(-surfGrad)`: direction decided almost entirely by height derivatives that spike at seams/panel edges, with no floor from the true geometric normal — producing dark/flipped-normal artifacts exactly at those edges, worsened by camera-angle-dependent rasterization (hence "moving"). This is also why (3) below had no gradation: `surfGrad` dominated regardless of its own magnitude once nonzero, and `normalize()` removes overall scale. **Fix:** `LitSurface.fx`'s `PerturbNormalFromHeight` now scales `ddx(renderPos)`/`ddy(renderPos)` by a new `RenderScaleReciprocal = 1e9` (1/`Camera3D.RenderScale`) constant before building `r1`/`r2`/`det`, restoring the physically-correct relative magnitude between `det` and `surfGrad`. **(2) Aliased/pixelated bump lines.** The height field's structural relief (seam grooves, panel steps) was a hard 1-2px edge — a near-discontinuous step differentiates to a near-discontinuous gradient, which the shader amplifies straight into aliasing. Albedo/gloss keep their existing hard edges untouched (a colour/reflectance cue, not a relief one). **(3) Strength too high, no gradation.** Root cause was (1) — fixing the scale mismatch restores genuine separation between preset values. **Architectural note — FlightMode, not separate states:**
Atmospheric flight is a `FlightMode` enum within `SystemSpaceState`, not a separate
`GameState`. The sim thread and all ship state run continuously through the transition.
`FlightMode` controls which forces the sim applies and which render passes are active.

```csharp
public enum FlightMode
{
    Docked,
    SystemNewtonian,          // Engine-harmony-ceiling force-based Newtonian
    SystemSlipstream,         // Harmonic warp-speed flight
    AtmosphericNewtonian,     // Force-based atmospheric (gravity, drag, lift)
    AtmosphericSlipstream,    // High-speed atmospheric mode
}
```

}

## Key conventions

- **Rate properties** (`MaxPower`, `PowerConsumption`, reactor output): always **watts (W)**
- **Storage properties** (`MaxJ`, capacitors): always **joules (J)**
- **Thermal mass** (`HeatCapacity`): always **J/K** (joules per kelvin)
- Each tick: `energy (J) = power (W) × dt`
- No display scaling in simulation; `InstrumentMeter.ScaleFactor` handles unit conversion for gauges
- No MW or MJ in code — raw SI throughout
- Topic convention on DataBus: `ComponentName.ValueName`; multiple instances: `ComponentName_N.ValueName`
- `ShipRecord` must not appear outside `ShipBuilder`, `ShipExtensions`, and `ShipPersistenceService`
- `ShipBuilder` is the sole construction path for `Ship`

## Station generation — architecture summary

See `stations-ai.md` for full reference. Key facts:

- **Generation is deterministic** — same seed always produces same station
- **AO baked, directional light real-time** — AO (and self-illumination floor S, in vertex alpha) applied at generation time to vertex colours; the sun term is computed every frame in `LitSurface.fx` from the real world normal, so a rotating station is lit correctly (lighting-pipeline Phase A — see `Docs/station-lighting-pipeline-spec.md`).
- **Screen-space glow** — `StationLightInfo` list on `StationModel`; `DrawStationGlows` uses `BlendState.Additive` SpriteBatch pass after 3D scene
- **AnimTag stubs** — warning strobes tagged for future animation; renderer does not yet use them
- **Decoration order matters** — occupancy tracking ensures no overlaps; passes run in fixed order; AO and lighting always last
